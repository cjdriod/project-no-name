# One architectural improvement I'd make

Instead of using generic Markdown frontmatter everywhere, I'd take advantage of **Astro Content Collections with Zod schemas**. That gives you compile-time validation, so if you accidentally omit a required field like `start` or misspell `showInResume`, Astro will fail the build with a helpful error instead of generating a broken page.

For example, an experience entry would be validated against a schema requiring fields such as:

* `company`
* `position`
* `start`
* `end`
* `employmentType`
* `location`
* `showInResume`
* `technologies`

This makes the project much more robust as it grows.

## What we'll do next

I suggest we move into the design phase before writing any code. Specifically:

1. **Information Architecture** – finalize every page and section.
2. **Data Schema** – define all content collections and their fields.
3. **UI/UX Design** – create low-fidelity wireframes for desktop and mobile.
4. **Component Inventory** – list every reusable Astro component.
5. **Implementation** – start building with confidence, knowing the foundation won't need major changes.

I recommend treating this like a small product rather than a quick portfolio. Spending time on architecture now will save a lot of refactoring later, and you'll end up with a personal website that's easy to maintain for years.
